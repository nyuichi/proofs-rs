Authentication

Start a device request, display its code in your terminal, and open the returned verification URL. After browser authorization, poll for a token. Store the token securely and send it as Authorization: Bearer <token>.

Tokens expire after 90 days. Manage them in Settings. CLI tokens can import API lists, publish claims, and revise your claims. Other write operations require a browser session.

Device login example 
curl -X POST "$ORIGIN/auth/device/code" \
  -H 'Content-Type: application/json' \
  -d '{"client_id":"proofs-cli"}'

# Display user_code, open verification_uri_complete, then poll
# no more frequently than the returned interval (initially 5 seconds).
curl -X POST "$ORIGIN/auth/device/token" \
  -H 'Content-Type: application/json' \
  -d '{"client_id":"proofs-cli","device_code":"DEVICE_CODE","grant_type":"urn:ietf:params:oauth:grant-type:device_code"}'

For authorization_pending, continue polling. For slow_down, increase the interval by five seconds. For expired, denied, or consumed requests, start again. If terms change, accept them in the browser.

Conventions

Send JSON unless otherwise stated. Paginated lists return items and next_cursor; pass the cursor unchanged to get the next page. Use the same Idempotency-Key and identical JSON body when retrying a creation request. A stale revision or changed idempotency body returns 409.

Browser writes require a same-origin Origin and the X-CSRF-Token from GET /api/v1/me. CLI tokens do not use these headers. Errors contain error, with optional message and request_id.
